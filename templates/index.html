🔍 Busca Semântica (densa)

Filtrar por collection

0% (Mais resultados) 100% (Mais precisos)

Vetor denso (embedding OpenAI/Gemini) + similaridade de cosseno. Não gera resposta de LLM.

O que esta tela faz: busca densa — compara o significado da consulta com cada chunk, não as palavras exatas. Lista trechos ranqueados. Não chama LLM.

Na indexação (upload)

O documento vira chunks (~1000 caracteres, overlap 200). Cada chunk passa pelo modelo da collection (OpenAI text-embedding-3-small → 1536 dimensões, ou Gemini → 3072) e vira um vetor denso gravado no Qdrant (dense), com distância de cosseno.

Na consulta

O texto digitado passa pelo mesmo modelo e vira outro vetor. O Qdrant mede o cosseno entre esse vetor e o de cada chunk. O percentual na lista é score × 100.

  • 100% — vetores na mesma direção (muito parecidos).
  • 0% — sem relação de direção.

Slider de similaridade mínima

Corta trechos abaixo do corte. Com 70%, só entram chunks com cosseno ≥ 0,70 — valor alto; lista vazia costuma ser o corte, não a ausência de documento. Teste 0% ou 30–50% para ver mais resultados. A tela devolve no máximo 5 trechos.

consulta → embedding (OpenAI/Gemini)
           ↓
cosseno no Qdrant (vetor dense)
           ↓
filtro do slider → lista de chunks

Semântica vs léxica

Semântica (esta tela) Lexical
Vetor Denso (1536D ou 3072D) Esparso (termos)
Casa Paráfrase, sinônimo, sentido Palavra ou código exato
Score Cosseno 0–100% BM25 (ex.: 5,034; sem teto)
Exemplo “impressão 3D” ≈ “manufatura aditiva” precisa dos termos no texto

“Impressão tridimensional” pode achar um chunk sobre additive manufacturing ou EBM mesmo sem essas palavras, se o embedding achar o sentido próximo. Na léxica isso só entra se os tokens coincidirem.

O que esta tela não faz: não gera resposta em linguagem natural. Isso fica no Chat Multi-Agente. Clique no chunk da lista para ver o texto completo.

🔤 Busca Lexical (esparsa)

Filtrar por collection

O que esta tela faz: compara as palavras da consulta com as palavras de cada chunk (vetor esparso). Não usa embedding e não chama LLM.

BM25 nesta tela: cada chunk guarda a frequência dos termos (TF). Na consulta, o Qdrant aplica IDF — termos raros na collection pesam mais. O número à direita (ex.: 5,034) é o score de relevância dessa fórmula, não um percentual.

  • Maior score = mais relevante para os termos digitados.
  • Não tem teto 100%: 5,034 é simplesmente mais forte que 2,262.
  • Sobe se o termo aparece mais vezes no chunk e/ou se ele é raro nos demais documentos.

🏷️ Entidades (estudo)

O TF-IDF é calculado dentro desta collection

O que esta tela configura

Não é uma busca. É um estudo sobre uma collection: lê o texto dos chunks no Qdrant, extrai termos e entidades e monta um rascunho para o golden set. Não altera a collection, não grava payload e não chama LLM.

Os três controles acima/abaixo

  • Collection: universo do estudo. O TF-IDF (o quanto um termo é distintivo) é calculado só entre os chunks desta collection — não mistura com outras.
  • Máx. chunks: quantos trechos serão lidos (teto 2000). Menos = mais rápido; mais = cobertura melhor. Chunks além do limite são ignorados.
  • Top N: quantos candidatos entram nas tabelas e no JSON (5 a 200). Não muda a extração, só o tamanho da lista final.
  • Top vizinhos: quantos tokens imediatos listar à esquerda e à direita de cada termo TF-IDF (1 a 30; padrão 5).

Três camadas combinadas

  • TF-IDF: termos que pesam neste documento e são raros nos outros (ex.: extrusão, lâminas). A coluna Antes/Depois mostra vizinhos imediatos, sem artigos e preposições.
  • NER (spaCy 3.7+ pt_core_news_md): pessoas (PER), organizações (ORG), lugares (LOC) e outros (MISC). Não use spaCy 3.0 — incompatível com Python 3.12.
  • Regex: o que o spaCy de notícias não pega — leis, pregões, CNPJ, processos, siglas (PC 1/2018).

Score = TF-IDF × IDF × peso do tipo

Multiplicação, não soma. Termo raro e típico do chunk sobe; código e sigla pesam mais que nome próprio, que pesa mais que termo só TF-IDF (código 3,0 → sigla 2,8 → PER/ORG 2,5 → local 2,0 → MISC 1,5 → TF-IDF 1,0).

Para o golden set (item 29)

O JSON é um rascunho de consultas, não o gabarito. Cada item traz categoria (nome próprio, sigla, código, frase exata, lexical) e candidate_points (chunks onde o termo apareceu). Você confirma quais Points são relevantes antes de calcular Recall@K / MRR. O botão Baixar JSON exporta esse rascunho.

Para o estudo visual (item 30)

Entidades que atravessam vários documentos viram sugestão de study_group (assunto). Use isso para colorir/agrupar uma collection temporária de comparação — esta tela não escreve isso nas collections de produção.

Treinar GLiNER (BIO → BERTimbau)

Serviço GLiNER desligado. Suba docker compose --profile gliner up -d --build gliner-bert com GLINER_BERT=true.

Treino no container Torch. O rag-demo não instala torch: envia o JSON BIO ao gliner-bert. Roda em CPU (mais lento) ou GPU se houver CUDA. O encoder é o BERTimbau; a cabeça GLiNER é treinada do zero.

  • Formato: tokens + ner_tags IOB2 (O, B-ROTULO, I-ROTULO).
  • O checkpoint vai para volumes/gliner-checkpoints/<nome>/.
  • Depois do treino, use Usar na extração (ou o seletor em Entidades GLiNER) — não precisa editar o .env.

Envie um JSON BIO para treinar (CPU ou GPU).

Exemplo mínimo

{
  "sentences": [
    {
      "tokens": ["O", "Tribunal", "de", "Contas", "analisou"],
      "ner_tags": ["O", "B-ORGANIZACAO", "I-ORGANIZACAO", "I-ORGANIZACAO", "O"]
    }
  ]
}
